01

Problem Statement

Why this project needed to exist

Raw datasets are never clean enough to model on. Every real-world CSV arrives with missing values, duplicate rows, outliers, wrong types, and inconsistent structure — and cleaning it is usually a one-off manual script that nobody can reproduce, audit, or trust six months later.

✕

No reproducibility — ad-hoc cleaning notebooks aren't versioned; re-running "the same" cleanup on new data gives different, undocumented results.

✕

No measurable quality — "the data looks clean" is an opinion, not a number. Teams have no consistent score to compare dataset versions or set a quality bar.

✕

No experiment or model trail — the imputers and outlier detectors fitted during cleaning are normally thrown away after use, so nobody can tell which model version fixed which dataset.

✕

No drift awareness — when new data starts looking statistically different from what a model was trained on, most pipelines have no way to notice until predictions quietly degrade.

✕

No operational visibility — without live monitoring, failures in the cleaning pipeline itself (bad uploads, mid-run errors) go unnoticed.

02

Proposed Solution

What DataPrep does about it

DataPrep is a full-stack platform — a FastAPI backend and a React frontend — that takes a CSV through one continuous, auditable pipeline: upload, validate, profile, repair, quality-score, and report. What makes it more than a cleaning script is that every stage is wired into real MLOps infrastructure running underneath it.

Cleaning, done right

A data-driven repair engine with no hardcoded per-dataset rules: structural fixes, type inference, duplicate removal, KNN/most-frequent imputation, outlier handling (IQR / Isolation Forest), low-variance column pruning, and CleanLab label-error detection.

MLOps, done underneath

DVC versions every stage automatically, MLflow logs every run as an experiment, fitted models enter a Model Registry with stage promotion, drift is checked on every re-upload, and detected drift can trigger closed-loop auto-retraining and redeployment.

03

Objectives

What the system set out to achieve

  1. Automatically detect and repair common data quality issues without hardcoding rules per dataset.
  2. Produce a quantifiable, weighted quality score with a full before/after audit trail.
  3. Version every dataset stage automatically so any past version can be reproduced on demand.
  4. Track every repair run as an experiment — parameters, metrics, execution time, artifacts.
  5. Treat the fitted imputers/outlier detectors as first-class models with a promotion lifecycle, not throwaway objects.
  6. Detect statistical drift on re-upload and close the loop with automatic retraining and redeployment.
  7. Give operators live visibility into pipeline health through a monitoring dashboard that survives MLflow-side failures.
04

Uniqueness

What goes beyond a typical "upload → clean → download" tool

Automatic per-stage DVC versioning

Every /upload, /profile, and /repair call transparently dvc adds its output — re-running the same file produces a new tracked version (v1 → v2 → v3) with zero manual DVC commands.

Drift-aware uploads

Re-uploading a filename seen before automatically diffs the new data against the last version — KS test per numeric column, missing-rate delta, outlier-rate delta — surfaced directly in the upload response and UI.

Closed-loop auto-retraining

Detected drift doesn't just alert — it re-fits the KNN Imputer and Isolation Forest, re-scores quality, registers new model versions, and auto-promotes to Production once quality clears 75%, archiving the previous Production version.

Independent monitoring store

monitoring.db is a separate SQLite log from MLflow specifically so failures that never reach MLflow — bad uploads, 404s, mid-pipeline errors — are still counted and visible.

11

Testing & CI/CD

How correctness is enforced on every change

Backend test suite

pytest + httpx, covering health/monitoring/registry shape checks, an upload → profile → repair pipeline smoke test, and drift-detection unit tests — run against an isolated scratch directory (MLOPS_TEST_ROOT) so tests never pollute the live dev server's databases.

GitHub Actions

Two parallel jobs on every push/PR: backend (install → pytest → import sanity check on Python 3.13) and frontend (npm ci → vite build on Node 20). Scoped to build+test only — no deploy step yet.

How to Present This — Suggested Flow

A ~15-minute walkthrough order, timed for a review slot

0–1 min

Open with the problem

State it in one line: "raw datasets are never clean enough to model on" — then name two concrete pains (no reproducibility, no drift awareness). Don't read the whole list; pick the two that hit hardest.

1–3 min

Introduce the solution

One sentence: upload → clean → score → report, with real MLOps infrastructure running underneath. Point at Section 2's two cards — "cleaning" vs "MLOps" — as the two halves of the pitch.

Tip: have the app running in a second browser tab, ready on the Upload page.

3–6 min

Live demo — the pipeline

Upload a CSV → show validation → Analysis page → Repair Result (the audit log) → Quality Report (before/after score, download a PDF). This is the core "wow" — let the product speak.

6–8 min

Walk the architecture diagram

Use Section 5's diagram. Trace one path out loud: "Repair calls preprocessing, which calls quality scoring, report generation, MLflow logging, and DVC versioning — all in one request." This is where you show engineering depth.

8–11 min

Show the MLOps layer live

Open the Monitoring page (live stats + Model Registry state) and, if time allows, the MLflow UI at localhost:5000. Re-upload the same filename to trigger drift detection on screen — it's the most memorable moment in the demo.

11–13 min

Name what's unique

Hit Section 4's four cards fast: automatic DVC versioning, drift-aware uploads, closed-loop auto-retraining, independent monitoring store. This is your differentiation answer if asked "how is this different from a cleaning script?"

13–15 min

Close with phases done + roadmap

One line: "16 phases shipped end-to-end, from project setup through CI/CD" — then name one or two roadmap items (auth, Docker) to show you know what's left, not just what's built.

Tip: if asked about scale, answer from the Roadmap section — don't improvise architecture changes live.
